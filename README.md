# 분당 버스 흐름

공공데이터 기반 버스 위치 추정 프로젝트의 첫 MVP입니다. **기본 화면과 클라우드는 시뮬레이션이며, 로컬에서는 720-2번의 실제 GBIS 연결을 확인했습니다.** 2026-10-16 처음으로 공개 위치상태 변경 간격을 관측했습니다. 원천 GPS 갱신 주기는 측정할 수 없습니다.

## 실행

Node.js 22 이상에서 프로젝트 폴더를 열고 실행합니다. 별도 패키지 설치가 필요 없습니다.

```powershell
node --env-file-if-exists=.env server.mjs
```

표시된 주소 `http://127.0.0.1:4317`를 엽니다. 온라인 미리보기는 시뮬레이션 전용이며, 로컬 서버에서만 GBIS 키를 사용합니다.

## 클라우드 접속

[분당 버스 흐름 열기](https://bundang-bus-lab.vercel.app/)

2026-10-16 Vercel 배포를 완료했습니다. 배포에 사용한 Vercel 계정으로 로그인하면 다른 컴퓨터와 휴대전화에서도 접속할 수 있습니다. 운영 주소를 포함한 모든 배포에 Vercel Authentication을 적용했습니다.

클라우드에는 `dist`의 지도 시뮬레이션 파일만 배포했습니다. 현재 실시간 GBIS 서버와 관측 도구는 로컬 실행용입니다. 키 발급 후 클라우드에서도 실제 버스를 조회하려면 서버 API 배포와 호출 예산 관리를 추가해야 합니다.

## 구현된 기능

- Leaflet 2D 지도 + OpenStreetMap 배경, 구간별 표시 선택, 정류소 표시, 차량 선택.
- 서현–야탑 / 정자–서현 / 판교–이매의 **직접 만든 예시 경로**와 가상 차량 6대. 공식 도로 형상·버스 노선·정류장 위치가 아닙니다.
- 10초 간격 시연 샘플과 노선 누적 거리 기반 보간. 이 10초는 시뮬레이션 설정값이며 GBIS 측정 결과가 아닙니다.
- 보간 전후 비교, 시연 정지·재생, 구간 평균 추정속도. 수신 좌표 이후로 외삽하지 않습니다.
- GBIS v2 서버 연결 준비: 노선 형상·정류소·운행 상태 조회, 응답 캐시, 중복 요청 합치기, 키 비공개, 실패 안내.
- 관측 도구: 차량별 상태 변경 간격 p50/p90/p95, 동일 상태 비율, 응답 시간, 필드 목록, JSONL 기록. 실패/누락 후 재등장은 새 관측으로 처리합니다.

## 실제 노선과 인증키 연결

1. 공공데이터포털에서 **경기도 버스위치정보 조회 서비스**와 **버스노선 조회 서비스**를 찾아 활용 신청합니다. 승인 화면의 실제 호출 한도를 확인합니다.
2. `.env.example`을 `.env`로 복사하고 `GBIS_SERVICE_KEY`에 Decoding 키를 넣습니다. 이 파일은 Git에서 제외됩니다. 채팅·브라우저·소스 코드에 키를 넣지 마세요.
3. 아래 검색을 실행합니다. `720-2`는 2026-10-16 공식 응답으로 분당 경유를 확인했고 ID는 `234000026`입니다. `33`, `17`은 아직 검증하지 않은 후보입니다.

```powershell
node --env-file-if-exists=.env scripts/discover.mjs 720-2
```

4. 운행지역·기종점을 확인하고 후보 ID의 공식 경유 정류소에서 분당 범위를 검증합니다. `.env`의 `GBIS_ROUTE_IDS`에 **번호가 아닌 routeId**를 최대 3개 지정합니다. 서버 `/api/routes`에서 공식 정류소와 좌표를 확인할 수 있습니다. 검증한 노선 이름은 `data/routes.json`에서 관리하고, 등록하지 않은 노선은 ID로 표시합니다.
5. `GBIS_DAILY_BUDGET`을 승인받은 남은 호출 예산 이하로 조정하고 서버를 다시 실행합니다. `GBIS 연결`에서 실데이터를 봅니다. 검증된 정류소 순번+ID가 일치하고 형상과 200m 이내로 매칭된 차량만 지도에 표시합니다.

서버 기본 예산 1,000회는 **보수적으로 정한 설정값**이며 공식 쿼터가 아닙니다. 폴링 간격은 `max(15초, 86400초 × 노선 수 / (예산 × 0.9))`입니다. 세 노선·1,000회 설정이면 약 288초이므로 세밀한 관측이 어렵습니다. 계정 한도 확인 후 올리세요. 호출 수는 `.local/quota.json`에 한국 날짜 기준으로 저장합니다. 단일 로컬 서버용이며 관측 도구·다른 프로그램의 소비량은 합산하지 않습니다. 노선 메타데이터 호출, 별도 실험분도 계정 총량에서 계산해야 합니다.

## 갱신 간격 관측

노선 ID를 확정한 뒤 서버의 실데이터 조회를 중지하고 별도 관측을 실행합니다. 다음 예시는 5초 간격·120초·최대 24회입니다. 승인량을 확인한 경우에만 2초 등으로 줄입니다.

```powershell
node --env-file-if-exists=.env scripts/probe.mjs --route=확정한노선ID --interval=5000 --duration=120 --max-requests=24
```

결과는 `measurements/실험시각/samples.jsonl`, `report.json`에 저장됩니다. 인증키를 저장하지 않으며 차량 식별자는 실험마다 다른 가명으로 기록합니다. 원본 차량번호는 기록하지 않습니다. 최소 두 번의 상태 변화가 있어야 변경 간격 표본이 하나 생깁니다. 표본이 없으면 수치를 만들어 내지 않고 `null`로 남습니다. 원천 GPS 주기·위치 정확도·실제 차량 지연은 이 실험으로 확인할 수 없습니다.

2026-10-16 첫 관측: 720-2번을 5초 간격으로 24회 조회해 오류 0회, 차량별 상태 변화 73건, 변경 간격 표본 50개를 얻었습니다. 중앙값 25.0초, p90 50.1초, p95 75.2초였습니다. 짧은 시간대의 정류소·운행 상태 변화 통계이며 API나 GPS의 고정 갱신 주기를 뜻하지 않습니다. 자세한 조건과 한계는 [검증 기록](docs/api-research.md)에 있습니다.

## 해석과 한계

GBIS 위치 명세에는 `vehId`, `plateNo`, `stationId`, `stationSeq`, `stateCd` 등은 있지만 차량 위경도·측정시각은 없습니다. `queryTime`은 요청시간입니다. 실제 위치는 공식 정류소와 노선 형상으로 계산한 **정류소 기준 추정**이며 순간속도가 아닙니다. 교차로 통과·출발 상태를 도로의 정확한 지점으로 환산할 수 없으므로 정류소 앵커를 유지합니다. 같은 상태가 반복돼도 실제 정차나 원천 미갱신으로 단정하지 않습니다.

위치가 역행하거나 비현실적인 속도가 계산되면 해당 속도를 버리고 새 기준점을 만듭니다. 왕복·회차 형상은 순번 순서로 정류소를 투영하지만 복잡한 중첩 노선에서 모호할 수 있어 실제 응답을 수동 검증해야 합니다. 실시간 실패 시 과거 표시는 지연 상태로 남으며 자동으로 시연 데이터로 바꾸지 않습니다. 오래된 속도는 숨깁니다.

핵심 자동 테스트는 합성 응답 기반이며, 720-2번은 실제 응답으로 정류소·형상과 차량 매칭도 확인했습니다. 배경지도는 인터넷 연결이 필요합니다. OSM 표준 타일은 MVP의 소규모 사용용이며 서비스 확대 시 제공사와 운영 조건을 재선정합니다.

## 단계별 범위

| 단계 | 상태 | 완료 기준 |
| --- | --- | --- |
| 공식 필드 조사 | 완료 | [검증 기록](docs/api-research.md) |
| 시뮬레이션 지도·보간 | 구현 | 경로 위 이동, 선택, 표시 제어 |
| GBIS 수집·관측 도구 | 720-2 실연동 확인 | 24회 실제 관측 및 변경 간격 보고서 생성 |
| 분당 실제 노선 1→3개 | 1개 확인, 추가 노선은 후속 | 정류소·방향·공식 형상 검증, 시간대별 관측 |
| VWorld 3D | 후속 단계 | 키·도메인 승인, 분당 커버리지·성능 확인 |

3D를 도입해도 `motion.mjs`의 좌표 계산은 그대로 쓰고 지도 표시 어댑터만 바꿉니다. GPS 정밀도가 향상되는 것은 아닙니다. 공식 3D SDK 연동 판단은 [조사 문서](docs/api-research.md)에 있습니다. 도착 예정시간·교통정체·진행방향 아이콘 회전은 현재 MVP 범위에 포함하지 않았습니다.
